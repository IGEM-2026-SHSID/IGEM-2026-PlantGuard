 # PlantGuard 双板 MicroPython 实现计划

  ## 概要

  - ESP32-C3 SuperMini 负责 DHT11、TSL2591 采集，建立 Wi-Fi 热点并提供手机页面和 HTTP API。
  - AI-Thinker ESP32-CAM 连接该热点，每 5 分钟拍照，或由 GPIO13 上升沿触发拍照。
  - ESP-CAM 使用 JPEG 解码器逐像素处理，但“蓝色区域识别与浓度计算”先保留独立算法接口，不擅自定义计算规则。
  - C3 保存最近 60 轮传感器数据和最近 60 次相机上报。最终计算公式未提供前，页面显示原始量和“结果未配置”。

  ## 实现方案

  ### ESP32-C3

  - 新建独立 ESP32-C3/ MicroPython 工程。
  - 默认接线：
      - TSL2591：SDA GPIO4、SCL GPIO5。
      - DHT11：GPIO3，启用上拉。
      - 所有引脚、周期、热点参数、历史容量、端口和超时统一放入 config.py。

  - 修正并迁移 TSL2591 驱动，正确处理：
      - 16 位通道寄存器读取。
      - 100–600 ms 积分时间。
      - 满量程溢出和非法 lux。
      - 原始 full-spectrum、infrared、visible 和 lux 输出。

  - 每 300 秒进行一次完整采样轮次，同时读取 DHT11 与 TSL2591；单个传感器失败不阻断服务。
  - 每条记录包含 C3 运行时间、温度、空气湿度、lux、原始光谱值、各传感器状态和错误信息。
  - 使用固定容量 RAM 环形历史，重启后清空，不写 Flash。
  - 最终计算放入独立 calculation.py，接口接收当前传感器记录和最近相机记录；公式未配置时返回 None 和 not_configured。
  - HTTP 服务使用短超时轮询，保证等待手机请求时仍能按周期采样。

  ### ESP-CAM

  - 保留现有 camera 固件接口和 GPLv3 JPEG 解码器，并补充依赖及许可证说明。
  - 相机默认配置为 JPEG、PSRAM、160×120；分辨率和 JPEG 解码质量放入 config.py。
  - 每 300 秒触发一次定时拍摄。
  - GPIO13 配置为下拉输入、上升沿中断；中断函数只设置待处理标志，拍照和网络操作在主循环执行，并进行软件去抖。
  - 定时与引脚触发同时发生时合并为一次拍摄，触发来源优先记录为 gpio，避免连续占用相机。
  - 图像处理采用像素回调结构：
      - JPEG 解码器输出 0xRRGGBB 像素。
      - blue_analyzer.py 接收坐标和 RGB。
      - 当前仅完成解码管线、尺寸及像素计数，蓝色值返回 None、状态为 algorithm_not_configured。
      - 后续只需替换分析器实现，不修改相机、网络和 API 流程。

  - 捕获、解码或上传失败时保留错误状态，执行垃圾回收并继续下一轮；Wi-Fi 断线后自动重连。
  - 不上传照片，只上传数值、处理状态和元数据。

  ## API 与页面

  - C3 热点默认地址为 192.168.4.1，SSID、密码和端口均从配置文件读取。
  - GET /：手机看板，显示温度、湿度、lux、光谱原始量、蓝色指标、最终结果、数据新鲜度和两块板状态。
  - GET /api/v1/state：返回当前传感器值、最近相机上报、最终计算结果和状态。
  - GET /api/v1/history/sensors：返回最近 60 轮传感器记录。
  - GET /api/v1/history/camera：返回最近 60 次相机记录。
  - POST /api/v1/camera/readings：接收 ESP-CAM 上报，限制请求体大小并校验 JSON 字段类型。
  - 相机上报字段固定为：
      - device_id
      - sequence
      - capture_uptime_ms
      - trigger：timer 或 gpio
      - width、height
      - decoded_pixels
      - selected_pixels
      - blue_value
      - error

  - C3 为上报补充本机接收时间，并返回 201；格式错误返回 400，路径或方法错误返回对应 404/405。
  - 设备 ID 仅用于区分来源，不做鉴权；已连接热点的其他客户端能够伪造上报，这是当前明确接受的边界。
  - 页面每 5 秒读取当前状态，但不会触发硬件重新采样；历史首版仅通过 API 提供，不添加趋势图。

  ## 测试与验收

  - 在普通 Python 环境中以硬件桩测试配置、环形历史、JSON 校验、HTTP 路由、异常状态和未配置计算结果。
  - 使用固定小型 JPEG 验证解码器能输出正确尺寸、像素数量和 RGB 回调。
  - 在 ESP-CAM 实机记录 160×120 捕获时间、解码时间、上传时间及解码前后可用内存；连续运行至少 20 轮，不得持续掉内存或重启。
  - 验证 GPIO13 单次脉冲只产生一次拍摄，抖动不会重复触发，定时触发仍可继续运行。
  - 验证 ESP-CAM 断开热点、C3 暂时不可达和 HTTP 上传失败后能够重试并恢复。
  - 验证 DHT11 或 TSL2591 单独断开时，页面和 API 仍可访问，并明确显示失败或数据过期。
  - 手机连接热点后验证看板和三个读取 API；相机成功上报后，C3 的当前状态与相机历史同步更新。
  - 若纯 MicroPython 解码在 160×120 下仍发生内存不足，先优化或改造 JPEG 解码实现；不在未验证的情况下提高到 320×240 或 640×480。

  ## 明确假设

  - 两块板均使用 MicroPython；相机固件已提供可用的 camera.init() 和 camera.capture()。
  - DHT11 测量的是环境温度与空气相对湿度，不解释为土壤湿度。
  - 本次不加入旧需求文档中的土壤湿度、告警、LoRa、模型推理或 App 推送。
  - 采样和定时拍照默认均为 5 分钟，配置项彼此独立，之后可以分别调整。
  - 蓝色区域判定、平均浓度定义及 C3 最终计算公式等待后续明确，不使用临时公式或蓝色通道透传冒充最终结果。
